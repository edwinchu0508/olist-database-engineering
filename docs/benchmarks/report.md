## E1: Does looking up one person by customer_unique_id need its own index?

Query `q1_customer_order_history` (customer_unique_id = 8d50f5ea-df50-201c-cdce-dfb9e2ac8455), 3 runs.

Hypothesis, written before measuring:

> Only the key indexes exist, so the person's customer rows can only be found by reading all of customers (99,441 rows, 1,029 pages). Everything after that already has an index: orders by orders_customer_id_key, items and payments by the leading order_id of their primary keys. A B-tree on customer_unique_id should make the whole query a chain of index lookups and take it from milliseconds to well under one.

## E2: What does the unindexed foreign key order_items.seller_id cost?

Query `q2_seller_recent_orders` (seller_id = 6560211a-19b4-7992-c366-6cc44a7e94c0, as_of = 2018-09-01), 3 runs.

Hypothesis, written before measuring:

> PostgreSQL does not index the referencing side of a foreign key. The seller has 2,033 of the 112,650 items, so the reference reads all of order_items (1,502 pages). A B-tree on seller_id finds the 2,033 directly, but seller_id has no physical correlation (0.003), so the bitmap heap scan still visits many of the 1,502 pages, and the orders of those items must still be read for the 30-day filter. Expect a real gain, smaller than E1's.
