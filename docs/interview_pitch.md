# 面试表达：三个案例各一分钟

每个案例按「选择 → 证据 → 代价」讲，约 300 字（含数字和英文术语），正常语速一分钟。下面依次是讲稿、必须记住的数字，以及常见追问的短答。详细版（英文）见 [interview_cases.md](interview_cases.md)；所有数字都能在仓库里找到出处。

## 1. 数据质量与建模：谁是客户

**讲稿**

> **选择：** Olist 的客户表有两个标识。我把 `customer_id` 当订单级标识，把 `customer_unique_id` 当真正的人；客户表保持每单一行，不另建「人」表。
>
> **证据：** 99,441 个订单正好对应 99,441 个 `customer_id`，但人只有 96,096 个，其中 2,997 人复购。按 `customer_id` 算，复购率和 cohort 留存都是 0。另外 250 人有多个邮编：地址属于订单，硬建「人」表就得替他们挑一个地址，等于编造数据。
>
> **代价：** 我用唯一键固定「一单一个 `customer_id`」。为了让加载能处理两单互换 `customer_id`，这个键必须可延迟检查（DEFERRABLE），代价是优化器不能用它证明唯一性，比如用不到的 LEFT JOIN 不会被消除。我验证过并接受了。按人查询另建索引：3.09 → 0.20 ms。

**必记数字：** 99,441 单 / 96,096 人 / 2,997 复购（3.12%）/ 按 `customer_id` 为 0 / 250 人多邮编、39 人跨州 / 索引后 3.09 → 0.20 ms

**追问**
- *为什么不建一个只含人的维表？* 可以建，只放 `customer_unique_id`。地址必须留在订单层，因为源数据没有「主地址」，选哪一个都是编造。
- *DEFERRABLE 还有什么限制？* 不能被外键引用。检查推迟到提交时，但只在发布事务里推迟：它是 INITIALLY IMMEDIATE，普通语句仍然立即检查。
- *2,997 这个数怎么保证对？* 先在 pandas 画像（`scripts/profile_olist.py`）里独立算出，再用测试钉住。查询结果另外和一份纯 Python 的第二实现比对。

## 2. 加载失败保护：core 不会半新半旧，结果也不靠猜

**讲稿**

> **选择：** 一次加载要么整版发布，要么完全不动 `core`。CSV 先进全文本暂存表，跑完 38 项检查，再在一个事务里对每张表做 MERGE；同一事务把状态写成 succeeded，作为提交标记。
>
> **证据：** 最初我用常见的表替换：建 `core_next` 再改名成 `core`。我写的双连接测试发现，快照早于替换的 REPEATABLE READ 读者看到 `orders` 是 0 行而不是 99,441 行：替换表的 DDL 对它不是 MVCC 安全的。改成 MERGE 后同一测试通过，每种失败也都有测试。
>
> **代价：** 提交时断线，客户端不知道提交了没有。我新开连接确认，5 秒内确定不了就报「未知」，退出码 3，和失败的 1 区分。审查发现确认查询被锁住会一直等，我给每条语句加 `statement_timeout` 补上。MERGE 的代价是逐行维护索引、留下死元组。

**必记数字：** 38 项检查（10 阻断、28 警告）/ 0 行 vs 99,441 行 / 5 秒期限 / 退出码 0 成功、1 失败、3 未知 / 首次加载约 25 秒，重复加载 0 行变化

**追问**
- *为什么不用 TRUNCATE 加 INSERT？* TRUNCATE 本身也不是 MVCC 安全的：快照早于它的事务会看到空表。它还要 ACCESS EXCLUSIVE 锁，会挡住所有读者。MERGE 只改变化的行，重复加载同一份数据一行都不写。
- *5 秒为什么还可能超？* libpq 的 `connect_timeout` 以整秒计、最少 2 秒，正在进行的连接尝试每个地址最多超 2 秒。这一点写在 limitations 里。
- *两个加载同时跑怎么办？* 会话级 advisory lock 让加载串行。拿到锁就证明没有别的加载器还活着，所以可以把遗留的 `running` 标成 abandoned。

## 3. 查询优化：4 倍提速，大部分不是索引的功劳

**讲稿**

> **选择：** Q3 查未完成订单，只占 1.7%。我最后选了部分索引，只收录 5 个未完成状态。
>
> **证据：** 每个变体只改一个因素，结果一致才计时。加索引后从 31.6 ms 降到约 8 ms，看似快了 4 倍。但基准用的是并行扫描；关掉并行，同一查询只要 14.8 ms。所以大部分提速是避开了这台 Windows 机器上很贵的并行计划，索引本身大约快 2 倍。省下的也不是页数：未完成订单分散在整张表里，索引仍要碰 1,341/1,419 页，省的是对 97,712 行逐行判断。部分索引和全索引一样快，32 kB 对 696 kB。
>
> **代价：** 部分索引的谓词就是它的契约，状态集合一变就得重建，否则会被悄悄弃用。无效的结果我也发布了，比如 BRIN 在这个布局上完全无效。

**必记数字：** 31.63 → 7.86 ms（全索引）/ 8.12 ms（部分索引）/ 关并行 14.81 ms / 并行基准 p95 135.9 ms / 1,341 / 1,419 页 / 32 kB vs 696 kB / 噪声：同一计划单轮差 −16% 到 +7%

**追问**
- *为什么不直接调 `parallel_setup_cost`？* 这轮实验的因素限定为索引和 SQL 写法，并行设置只做诊断。调参是下一步，而且要在 Linux 上也测，因为这个开销跟平台有关。
- *怎么区分真实差异和噪声？* BRIN 变体和基准的计划完全相同，单轮 p50 仍差 −16% 到 +7%。所以差异在 15–20% 以内、计划又没变时，我不下结论。
- *BRIN 为什么无效？* BRIN 每 128 页只记最小值和最大值。购买时间的物理相关性是 −0.001，每个区间都几乎覆盖整整两年，所以强制使用时 1,419 页全部命中，再逐行复查丢掉 96,433 行。只有按时间顺序追加写入的表才适合 BRIN。
- *缓存是热的吗？* 是。66 个记录下来的计划全部在 shared buffers 命中，没有读盘；冷缓存没测，写在 limitations 里。
